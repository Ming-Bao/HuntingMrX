\begin{abstract}
\begin{itemize}
	\item Problem: hidden-movement board game limited to co-located play; existing digital versions use fictional boards and no real geography.
	\item Solution: browser-based, real-time multiplayer game on a 216-node, 372-edge graph of Wellington's bus, train, ferry, and e-scooter network.
	\item Method: Java/Spring Boot authoritative server, Vue 3 + MapLibre GL client, STOMP over WebSocket, role-filtered state so Mr~X's position is never sent to detectives.
	\item Evaluation: automated tests (134 backend tests across unit, mock, lifecycle, integration, functional and property-based/fuzz layers, plus an opt-in latency test; 99.2\% line and 97.8\% branch coverage; 100\% mutation score), map-library benchmark, two user-testing rounds, System Usability Scale (SUS) questionnaire (overall 72.5, n = 7, against the 68 average benchmark).
	\item Outcome: deployed, playable system suitable for Open Day demonstration.
\end{itemize}
\end{abstract}

\begin{IEEEkeywords}
Multiplayer game, hidden movement, real-time web application, WebSocket, map overlay, usability evaluation.
\end{IEEEkeywords}

	\item Gap: existing digital versions replicate the original board; no browser-based version on a real city map with real transport modes.

	\begin{itemize}

\section{Design} % ~3 pages
\subsection{Architecture}
\begin{itemize}
	\item Client--server, authoritative server; figure: browser (Vue + Pinia + MapLibre) / REST / STOMP / Spring Boot / in-memory \texttt{ConcurrentHashMap}.
	\item Why REST for actions and WebSocket for push only (simpler auth and error handling).
	\item Alternatives considered and rejected: peer-to-peer, polling, database-backed sessions, Node backend (Java vs JavaScript from the proposal); trade-off for each.
\end{itemize}
\subsection{Game State Machine and Turn Flow}
\begin{itemize}
	\item Phases: Lobby, InProgress (MrXTurn, DetectiveTurn, RoundEnd), ended states (detectives win, Mr~X wins, aborted); the lobby closes if the host leaves (figure from \texttt{plans/states-diagrams.md}).
	\item Every operation validated against phase (e.g.\ start only in lobby, kick only in lobby).
	\item Leaving and idling: any player leaving a game in progress aborts it, and the server aborts a game after 15 minutes without a move. Pause-on-disconnect with a 60 s grace period was planned but dropped: user-testing networks dropped WebSockets often, so clients reconnect and re-sync over REST instead of the server pausing.
\end{itemize}
\subsection{Domain Model}
\begin{itemize}
	\item Player model: one \texttt{Player} class whose role is assigned at start; every rule lives in a plain \texttt{Game} class with no Spring, which made the rules directly unit-testable (the earlier lobby/Mr~X/detective class hierarchy and abstract player were collapsed in the backend rewrite).
	\item Ticket model: unlimited regular tickets for Mr~X, finite Invisible and Double; fixed budgets for detectives.
	\item Class diagram (from \texttt{plans/classdiagram.md}).
\end{itemize}
\subsection{Hidden Information and Role-Filtered State}
\begin{itemize}
	\item Each player receives a filtered snapshot; Mr~X's node omitted on non-reveal rounds, reveal appears in log.
	\item Per-player topics rather than one shared topic (explain why).
	\item Sequence diagram of a move: submit, validate, apply, catch check, broadcast per-player views.
\end{itemize}
\subsection{Map Data Design}
\begin{itemize}
	\item Decision: static graph JSON with inline GeoJSON geometry versus live routing APIs (cost, latency, hundreds of edges).
	\item Node and edge format, undirected edges, mode arrays; graph density and balance between the four modes.
	\item Library selection: benchmark methodology and results (see Evaluation).
\end{itemize}
\subsection{User Interface Design}
\begin{itemize}
	\item Screens: landing, create, join, lobby, game board, end screen; dark theme, mode colours, ticket selector, info panel, Mr~X log with reveal rows.
	\item Design decisions tied to feedback (see Evaluation): transport-mode popups, viewport-relative layout, centred turn indicator.
	\item Mockups or Figma reference (if used).
\end{itemize}
\subsection{Real-World Issues}
\begin{itemize}
	\item Ethics: voluntary student participants, course coordinator approval; vouchers for participants (check the ethics wording).
	\item Sustainability: no per-request cloud calls, minimal self-hosted infrastructure.
	\item Safety and IP: no location tracking of real players; Ravensburger permission; open-source licences (GPL-3.0 for repo; map data attribution).
	\item Privacy: what is stored (in memory only), no accounts.
\end{itemize}

	\item Technology table with justification: Java 21, Spring Boot 4.0.6 (\texttt{spec.md} says 3, verify), Maven; Vue 3, Pinia, Vue Router, TypeScript, Vite, Tailwind CSS 4; MapLibre GL 4; \texttt{@stomp/stompjs} and SockJS; Docker, nginx, supervisord, Cloudflare Tunnel.

	\item Move validation: edge lookup, ticket check, occupied-node rule, catch detection, auto-skip of stuck detectives; per-game locking for concurrency.

	\item Double move and Invisible ticket handling; log entries for each leg.
	\item Configuration properties: grace period, turn timer, detective ticket budgets (12 e-scooter / 8 bus / 6 train / 2 ferry).
	\item Frontend: Pinia store as single source of truth, STOMP subscriptions, REST fallback with polling for reconnect (6 s), MapLibre layers per mode, reachable-node highlighting, node popups.

	\item Deployment: single Docker image (nginx + Spring Boot under supervisord), \texttt{BASE\_PATH} support, update script, Cloudflare Tunnel on a home server; live at the deployed domain.
	\item API documentation: OpenAPI spec (currently 0.1.11) kept in sync with REST and STOMP topics, enforced in the workflow.

\section{Evaluation} % ~3.5 pages
\subsection{Map Library Benchmark}
\begin{itemize}
	\item Method: Selenium + Firefox, 10 runs each, baseline and stress scenarios (\texttt{time\_maps.py}, \texttt{scenarios.json}).
	\item Results table (mean, s): baseline Google 0.70 / Leaflet 0.23 / MapLibre 0.40; stress 2.69 / 2.21 / 2.31.
	\item Discussion: Leaflet fastest but MapLibre gives WebGL and lowest variance in stress; Google needs a key and cost; MapLibre chosen. Note that the benchmark measured empty-map and synthetic load, not the final graph.
	\item Threats: single browser, single machine, small run count.
\end{itemize}
\subsection{Functional Correctness}
\begin{itemize}
	\item Test suite: 134 backend tests: unit (82: \texttt{MapGraph}, \texttt{Player}, \texttt{Game} on hand-drawn boards), mock (17: \texttt{GameService} with mocked messaging), lifecycle (8 scripted complete games), integration (19: HTTP via MockMvc, STOMP with real clients), functional (4: full games over HTTP and STOMP), property-based and fuzz (4, JUnit with seeded random), and performance (1, opt-in); mapped to the proposal's plan.
	\item Table of layers, counts and what each catches (counts and results in \texttt{documentation/backend-fixes.md}).
	\item Targeted tests: every bug found in the backend review has a regression test (\texttt{documentation/backend-fixes.md}), e.g.\ Mr~X boxed in, chained double moves, hidden position not leaked over REST or STOMP.
	\item Full-game end-to-end test through the real server with an HTTP and a STOMP client for every player (it replaced a Selenium test that only used the browser as an HTTP client and was flaky).
	\item Meta-testing: JaCoCo coverage 99.2\% lines and 97.8\% branches overall (game and service: 99.7\% and 97.7\%); PIT mutation score 100\% (201 of 201 mutants killed) on game and service, after the first run's survivors exposed seven missing tests; property-based tests over 300 seeded random games (every rule holds and every game ends) and fuzz tests (garbage moves, names and request bodies never cause a server error). Frontend has no automated tests.
\end{itemize}
\subsection{Performance and Multiplayer Synchronisation}
\begin{itemize}
	\item Targets: 500 ms push latency, 3 s map render, concurrent games.
	\item Latency harness (\texttt{MultiplayerPerfTest}): 10 concurrent games of 6 players on the real map (987 moves); move submitted to every other player updated p50 4.6 ms, p95 8.3 ms, max 36.6 ms, against the 500 ms target. A render-time measurement with the real map is still to do.
	\item Report percentile latencies as a figure/table; compare against targets.
\end{itemize}
\subsection{User Evaluation}
\begin{itemize}
	\item Participants: seven players (six detectives, one Mr~X), games of four to six players; voluntary, ethics approved, voucher incentive.
	\item Instrument: SUS plus free-text comments and role / player count / perceived side balance.
	\item Results table: Mr~X 70.0 (n = 1), detectives 72.9 (n = 6), overall 72.5 (n = 7); above the 68 benchmark; range 60--95.
	\item Qualitative themes: onboarding and tutorial demand (three responses), Mr~X log hard to read at first, reachable-node scaling on small screens, praise for fun and replayability, request for custom lobby rules.
	\item Iteration evidence: test round one (seven issues) and round two (four issues) mapped to the fixes (name limit, zoom limit, tall log, node popups, final-state view, colour diversity, selection highlight bug, centred turn indicator, reveal rows in log, unabbreviated rounds).
	\item Limitations: small n, one Mr~X respondent, convenience sample of students, SUS tested after fixes were partly applied. Possibly add before/after comparison if a third round is run.
	\item Side balance: column ``which side felt stronger'' was answered 2 by everyone; decide how to interpret and report (check the form's scale).
\end{itemize}

\section{Discussion} % ~0.5 page
\begin{itemize}
	\item What worked: pre-computed graph, authoritative server with filtered views, simplification refactor (about 287 lines removed with all tests green); the backend rewrite into a plain rules core plus a thin Spring service (rules directly unit-testable, eight bugs fixed with regression tests).
	\item What was hard: map creation effort, disconnect and reconnect behaviour, in-memory state means a restart ends all games.
	\item Security lesson: role filtering was bypassable, because public player IDs doubled as credentials and the in-memory STOMP broker honoured wildcard subscriptions and client SENDs; fixed with secret tokens, exact-match subscriptions and dropping client SEND frames.
	\item Trade-offs revisited: no accounts (per-player secret tokens instead), no database, desktop-first layout.
	\item Threats to validity: small sample, no automated frontend tests, benchmark scope.
\end{itemize}
