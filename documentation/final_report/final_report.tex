\begin{abstract}
The current open day demo for VUW is over five years old and is outdated. A good demonstration matters because, for many visitors, it is their first look at the challenges they would face in the degree and at what a student can build by its final year. This project shows that a single fourth-year student can turn a classic hidden-movement board game, normally played around one table, into a complete real-time online multiplayer game on a real map of Wellington, playable from any desktop browser, and it was demonstrated successfully at an Open Day. The game gives future Open Days a playable conversation starter about real software development challenges, such as keeping every player's screen up to date and keeping one player's position secret.
\end{abstract}

\section{Introduction}

\IEEEPARstart{H}{idden-movement} games are board games in which one player moves in secret and the others try to work out where they are. In the best-known example, Scotland Yard by Ravensburger \cite{rules_1983}, one player (Mr~X) travels across a city by taxi, bus and underground while detectives chase him. His position is shown only on a few fixed rounds; in between, the detectives see only which kind of ticket he spent. The rules are simple, but a physical game has two limits: everyone must be in the same room, and the hidden player must record his moves honestly on paper.

An online version removes both. A server can hold Mr~X's position, check every move against the rules, and show each player only what they are allowed to see. Players can then join from their own device, from anywhere, with a link or code.

The project began when Jens Dietrich, the primary supervisor, suggested a hidden-movement board game as a demonstration for the university's Open Day.

\subsection{How the Game Is Played}\label{sec:rules}
\emph{Hunting Mr.~X} is played by two to six people. One is chosen at random to be Mr~X and the rest are detectives, who work together to catch him. The board is a map of Wellington with 216 numbered locations (nodes) joined by routes (edges). Each route is served by one or more transport modes: e-scooter, bus, train or ferry.
\begin{itemize}
	\item \emph{Moving.} The game lasts up to 24 rounds. In each round Mr~X moves first, then each detective in turn. A move goes along one route to a neighbouring node and costs one ticket for a mode that serves that route.
	\item \emph{Tickets.} Each detective starts with 12 e-scooter, 8 bus, 6 train and 2 ferry tickets. Each move uses a ticket, so detectives must plan. Mr~X has unlimited ordinary tickets.
	\item \emph{Hiding.} The detectives always see each other, but not Mr~X. After each of his moves they see only which ticket he used, recorded in a log. His position is revealed only after his move in rounds 2, 8, 13, 18 and 24.
	\item \emph{Special tickets.} Mr~X also has one Invisible ticket per detective, which works on any route and hides which mode he used, and two Double tickets, each letting him move twice in one turn.
	\item \emph{Winning.} The detectives win if one of them lands on Mr~X's node, or if he cannot move because detectives block every node next to him. Mr~X wins if he is still free after round 24.
\end{itemize}

\subsection{Problem}
The problem is deliberately narrow: \emph{build a browser-based, real-time multiplayer hidden-movement game, played on a map of a real city, in which the rules and the secret are enforced by the system rather than by the players.} Wellington was chosen because a familiar map makes the game instantly recognisable to local players and Open Day visitors.

The engineering difficulty lies in two places:
\begin{itemize}
	\item \emph{Server push to many clients.} Every move must reach all other players quickly, over busy networks, without any client being trusted with state it should not see. Every update is therefore several different messages, one per viewer.
	\item \emph{Separate frontend and backend languages.} The backend is written in Java and the frontend in TypeScript, so they cannot share code. Both sides must agree on the format of every request and message sent between them.
\end{itemize}

\subsection{Two Themes}
Two themes run through the project and shape decisions in every later section.

\emph{A showpiece for Open Days.} The university's Open Days need demonstrations that show prospective students what engineering students build, in a form a visitor can try in a few minutes. The software engineering demonstration in use before this project was over five years old and outdated. A new one should start conversations with visitors about the challenges they can expect in software development, and show what a fourth-year student can build. A game on a map of their own city, with no app to install or account to create, fits that purpose: several groups can play at once on the stand's laptops while a big screen shows the board.

\emph{Online multiplayer over the internet.} The board game can only be played by people sitting at the same table. Here each player joins from their own computer, wherever they are, using a link or a six-character code, and the server keeps every player's screen up to date as moves happen. This is what turns the board game into a networked system, and it is where most of the engineering effort lies.

Sustainability is a secondary consideration. Every transport mode in the game is a low-emission one (e-scooter, bus, train and ferry, with the board game's taxi replaced by the e-scooter), and the infrastructure was kept small; both points are discussed in Section~\ref{sec:design}.

\subsection{Goals}
The project has three goals, set in the proposal:
\begin{enumerate}
	\item Enforce every game rule on the server: movement, tickets, turn order, reveal rounds, the double move and Invisible ticket, and every end condition (requirements F1--F6).
	\item Never send Mr~X's position to a detective's browser except on a reveal round (F4).
	\item Reach a System Usability Scale (SUS) score above the average of 68 (N3).
\end{enumerate}
Section~\ref{sec:requirements} breaks these goals into numbered requirements. Those numbers are the backbone of the rest of the report: each design and implementation subsection begins by listing the requirements it addresses, and Section~\ref{sec:trace} checks every requirement against its evidence.

\subsection{Contributions and Findings}
The project delivers a deployed, playable game \cite{repo}; a curated, pre-computed graph of the Wellington region together with the tool used to build it; an authoritative server that filters state per viewer; and an evaluation combining a map-library benchmark, a layered automated test suite checked by coverage and mutation testing, and user testing with a usability questionnaire. All three goals were met. The main limitations are a small user sample and the lack of automated frontend tests.

The mechanics are used with Ravensburger's permission for this non-commercial academic project. The original name is not used, so the game is called \emph{Hunting Mr.~X}, and the board game's taxi is replaced by the e-scooter, the short-range, low-emission mode a Wellington player is most likely to use today.

Section~\ref{sec:related} reviews related games and technologies, Section~\ref{sec:requirements} sets out requirements and scope, Sections~\ref{sec:design} and~\ref{sec:implementation} describe the design and its implementation, Section~\ref{sec:evaluation} evaluates the result, and Sections~\ref{sec:discussion} and~\ref{sec:conclusion} discuss and conclude.

\section{Related Work}\label{sec:related}

\subsection{Map-Based and Location-Based Games}
Games that use real geography fall into two groups. \emph{Map-based} games use a real map as the board while the player sits still. GeoGuessr \cite{geoguessr} drops players into a street-level panorama and asks them to place it on a world map; its popularity shows that recognising real places is enjoyable in itself. But GeoGuessr's map is a backdrop for a guessing task: there is no movement network, and its multiplayer modes are races rather than games of hidden information between opponents.

\emph{Location-based} games such as Pok\'emon GO \cite{paavilainen2017pokemon} take the opposite approach and use the player's physical position, so the city itself is the board. Paavilainen \emph{et al.} \cite{paavilainen2017pokemon} attribute Pok\'emon GO's mass appeal partly to the fun of moving around the real world and the sociability it brings, but also note the drawbacks: players in rural areas have far fewer places to play, and some found the game's mechanics too simple.

This project sits between the two groups. It keeps the strategy of the board game and the recognisability of a real city, but moves the players' tokens rather than the players. That avoids the safety, accessibility and location problems of physical play while keeping the appeal of a familiar map.

\subsection{Existing Digital Versions}
Three digital versions of the board game were reviewed:
\begin{itemize}
	\item \emph{SSY} \cite{ssy} is a free website that enforces the rules. Mr~X scans a QR code with his own phone to see his position and options, while the detectives enter their moves on a shared screen. It is played in one room around one screen, not over the internet.
	\item \emph{Tabletop Simulator} \cite{tts} (NZ\$29 on Steam) is a physics sandbox in which players move pieces on a virtual copy of the board by hand. It can be played online, but it enforces no rules, so the game and Mr~X's secret depend on the players being careful and honest.
	\item The \emph{official PC adaptation} \cite{official_pc} (NZ\$22 on Steam, 2024) supports online play for up to six players on a redesigned London board, but had mostly negative reviews (23\% positive of 21) at the time of writing.
\end{itemize}
All three use the fictional printed board, and none is a free online game that can be opened from a link.

\subsection{Cheating in Online Games}
Making the game playable over the internet, one of this project's two themes, brings a problem the printed board game never has: keeping Mr~X's position secret when every player's device is connected to the game. Research on cheating in online games is therefore relevant to the design. If the server sends Mr~X's position to every player and the detectives' screens simply do not display it, a detective can still find it, for example by opening the browser's developer tools. Yan and Randell \cite{yan2005cheating} call this cheating by exploiting misplaced trust: too much trust is placed in the game client, which a cheating player fully controls, and they note that hiding how the client works only delays such cheating. The usual fix is to make the server the only part of the system that knows the full game state: players send the moves they want to make, the server decides what happens, and each player receives only what they are allowed to see. This was not a theoretical risk for this project. Earlier versions of the game had exactly this weakness: player identifiers that every client received also worked as credentials and players could request for Mrxs' location. The risk is greater because the project is open source. Anyone can read the repository to find which endpoints to call, and AI coding assistants make this easy even for players with little programming experience. A couple of user testers did exactly that, using AI to read the code and call the API directly to find Mr~X. Secrecy therefore cannot depend on the code being hidden; it has to come from the server refusing to give out information. Section~\ref{sec:hidden} describes how the final version does that.

\subsection{Sending Live Updates to Browsers}
In an online game, when one player moves, every other player's screen has to update straight away. Normally a browser only gets data when it asks for it, so there are three common ways to do this:
\begin{itemize}
	\item \emph{Polling:} the browser asks the server for the latest state every few seconds. This works everywhere, but updates are only as fast as the interval, and asking more often adds load on the server.
	\item \emph{Server-Sent Events:} the browser keeps one connection open and the server sends updates down it as they happen. Messages can only go from the server to the browser.
	\item \emph{WebSocket} \cite{rfc6455}: a connection that stays open and carries messages both ways.
\end{itemize}
WebSocket on its own just carries messages. STOMP (Simple Text Oriented Messaging Protocol) adds named channels, called topics, that a browser can subscribe to, which suits a game well: one topic per game, and one private topic per player. Spring, the Java framework used for the server, supports STOMP directly. SockJS is a browser library that falls back to ordinary HTTP when a network blocks WebSockets. Section~\ref{sec:architecture} explains which of these was chosen and why.

\subsection{Map Tools}
The game needs an interactive map of Wellington that can show the board's nodes and routes on top. Three map libraries were considered:
\begin{itemize}
	\item \emph{Google Maps} is the best known, but it is a paid service: usage is billed per request and needs an API key \cite{googlemaps_pricing}.
	\item \emph{Leaflet} is a free, open-source library. It draws the map using the web page's normal elements, which can slow down when many shapes are drawn.
	\item \emph{MapLibre GL JS} \cite{maplibre} is also free and open source. It draws the map with the computer's graphics card (through WebGL), which keeps it smooth with many shapes on screen.
\end{itemize}
The free libraries need map data from somewhere. OpenStreetMap (OSM) is a free, community-made map of the world whose road data can be used under an open licence \cite{osm}. Overpass Turbo is a tool for downloading part of it, such as all the roads in Wellington, and CARTO provides free map styles built from it.

The game also needs each route between two nodes to follow real roads. Routing services such as Google's can work out a road path between two points, but each request costs money and takes time \cite{googlemaps_pricing}. Using the free tools instead, the board can be built from real map data without paying per request. Sections~\ref{sec:mapdesign} and~\ref{sec:benchmark} explain how the tools were chosen.

\subsection{Measuring Usability}
The System Usability Scale (SUS) \cite{brooke1996sus} is a standard questionnaire for measuring how easy a system is to use. It has 10 statements, such as ``I thought the system was easy to use'' and ``I found the system unnecessarily complex'', which alternate between positive and negative. Each is rated from 1 (strongly disagree) to 5 (strongly agree), and the answers are combined into a single score from 0 to 100. The score is not a percentage: across hundreds of published studies the average is about 68 \cite{sauro2011sus}, so a score above 68 means a system is easier to use than most. SUS was chosen for this project, as planned in the proposal, because it takes players about two minutes after a game, is free to use, gives reliable results even with small groups, and lets the result be compared with that published average rather than judged on its own. The full questionnaire is linked in Appendix~\ref{app:sus}.

\section{Requirements and Constraints}\label{sec:requirements}

Each requirement has an identifier (F for functional, N for non-functional, C for constraint) that the later sections refer to.

\subsection{Functional Requirements}
The rules follow the board game \cite{rules_1983}, adapted to Wellington (Section~\ref{sec:rules}):
\begin{description}
	\item[F1] \emph{Lobby.} A host creates a game for two to six players and shares it by a six-character code, a link or a QR code. The host can remove players and start the game.
	\item[F2] \emph{Roles.} At the start, one player is chosen at random as Mr~X and the rest become detectives; everyone starts on a different random node.
	\item[F3] \emph{Movement.} Each move follows one edge and spends a ticket for a transport mode on it: e-scooter, bus, train or ferry. Each detective starts with 12, 8, 6 and 2 of these; Mr~X has unlimited ordinary tickets. Mr~X may not move onto a detective. A detective with no legal move is skipped.
	\item[F4] \emph{Hidden information.} Detectives see Mr~X's position only after his move in rounds 2, 8, 13, 18 and 24. Everyone always sees which ticket he used.
	\item[F5] \emph{Special tickets.} Mr~X holds one Invisible ticket per detective, which crosses any edge and hides the mode, and two Double tickets, each giving two moves in one turn.
	\item[F6] \emph{Ending.} Detectives win by landing on Mr~X or by leaving him no legal move; Mr~X wins by surviving round 24. A game ends early if a player leaves or the current player does not move for 15 minutes.
	\item[F7] \emph{Real map.} The board is a graph of real Wellington locations, with edges drawn along real streets and lines and coloured by mode.
\end{description}

\subsection{Non-Functional Requirements}
\begin{description}
	\item[N1] \emph{Standard hardware.} The game runs on an ordinary desktop or laptop in the current release of each of the three browser engines: Blink (Chrome, Edge), Gecko (Firefox) and WebKit (Safari). It needs only WebGL for the map and a WebSocket, or failing that HTTP streaming. No installation, plug-in or account is needed.
	\item[N2] \emph{Resilience.} A dropped connection must not end a game, and a client must catch up within seconds of reconnecting.
	\item[N3] \emph{Usability.} A SUS score above 68 \cite{sauro2011sus}.
\end{description}

\subsection{Constraints}
\begin{description}
	\item[C1] No paid per-request services such as metered routing or map APIs.
	\item[C2] Self-hosted on the author's existing home server, in a single container, with no database.
	\item[C3] One developer over 24 weeks, with a budget of \$500.
	\item[C4] The original game's name and branding must not be used.
\end{description}

\subsection{Scope}
The game has two audiences, and the scope follows from them.
\begin{itemize}
	\item \emph{Friends playing together} have already agreed to play and want a 30--60 minute game that is clear and fair. They play from their own computers and talk by voice or in person.
	\item \emph{Open Day visitors} try the game at a stand on the stand's laptops. A demonstrator introduces it and sets up the lobby, so the interface does not have to win a stranger's attention in the first 30~seconds on its own; it has to let a newcomer join in seconds and understand a move after one explanation.
\end{itemize}
\emph{In scope:} desktop browser play; sharing a game by link, code or QR code; starting the whole server from one container image; and everything in F1--F7.
\emph{Out of scope:} user accounts and saved games; a mobile-first layout; computer-controlled opponents; in-game chat; and any use of players' real locations.

\section{Design}\label{sec:design}

\subsection{Architecture}\label{sec:architecture}
\reqs{F4, N1, N2, C1, C2}
The system is a client--server design with an \emph{authoritative} server (Fig.~\ref{fig:architecture}). The server holds every game in memory, applies every rule, and decides what each player may see. Browsers send intentions (``move to node 42 by bus'') as Representational State Transfer (REST) calls and receive state on STOMP topics; they never compute an outcome themselves.

The alternative considered was a \emph{host-authoritative} design, in which the host's browser runs the rules and the other players connect to it. It was rejected for two reasons. The host's browser would hold the full game state, including Mr~X's position, so whenever the host played as a detective the secret would be on their device, breaking goal~2. And the game would end for everyone if the host closed the tab or their laptop went to sleep. A dedicated server avoids both problems, and it suits C2 because the home server already existed.

\emph{How browsers and the server talk.} Communication is split into two directions:
\begin{itemize}
	\item \emph{Player actions} (create, join, start, move, leave) are ordinary web requests (REST). The main reason is error handling: when a move is illegal or it is not that player's turn, the server can simply reply with an error code and a message, which the browser shows to the player. Ordinary requests are also easy to test.
	\item \emph{Updates} travel the other way over STOMP on a WebSocket. In the lobby, each browser subscribes to the game's public topic. On the game board it subscribes instead to two private topics named by the player's secret token: one for the player's own view of the game and one for their legal moves. The server pushes new state to these topics as soon as anything changes. Browsers only subscribe and listen; any message a browser tries to send on this connection is dropped by the server.
\end{itemize}
The other options from Section~\ref{sec:related} were rejected. Polling alone would make every move take up to one polling interval to appear on other screens (6~s at the rate used here). Server-Sent Events could push updates just as quickly, but STOMP's topics already give one channel per game and per player without extra code, and SockJS lets the connection fall back to ordinary HTTP on networks that block WebSockets (N1). Polling is still used as a backup in case a pushed update is missed (Section~\ref{sec:resilience}).

\emph{No database.} A game lasts under an hour and only exists while its players are online, so all games live in a concurrent hash map. A server restart ends every game; this is accepted for this version (C2) and listed as future work.

\emph{Two languages, one contract.} Java was chosen for the server over Node.js because Spring provides a STOMP broker out of the box, and Java has mature coverage (JaCoCo) and mutation (PIT) tools for the test-quality measures promised in the proposal. The cost is that client and server cannot share types. The design answers this with one written contract: an OpenAPI 3.1 file documenting every REST endpoint and every STOMP topic, which must change in the same commit as any change to either side (Section~\ref{sec:process}).

Two rules cover players who stop playing; neither comes from the board game, which assumes everyone stays at the table.

\emph{Leaving ends the game.} If a player presses Leave during a game, the game ends for everyone with a message naming who left. Continuing without them was rejected. Without Mr~X there is no game, and without a detective the game is no longer balanced, because Mr~X's number of Invisible tickets is set by the number of detectives at the start. Handing the missing player's role to someone else would not work either. Ending the game is also the simplest rule to make correct. Losing a connection or refreshing the page is not leaving: the player keeps their place and catches up when they reconnect (Section~\ref{sec:resilience}).

\emph{Idle games are ended after 15 minutes.} If the player whose turn it is makes no move for 15 minutes, the game ends. Without this, a closed or forgotten tab would leave the other players waiting indefinitely, and the server would keep the game in memory forever. Shorter limits, or skipping a slow player's turn automatically, were rejected because players among friends often discuss a move for several minutes; 15 minutes is far longer than any turn in play-testing, so it only catches abandoned games.

\subsection{Domain Model}\label{sec:domain}
\reqs{F1--F6}
All rules live in three plain Java classes with no framework dependency: \texttt{Game} (lobby, start, moves, turns, reveals, endings, leaving, the idle abort and per-viewer views), \texttt{Player} (identity, role, position and tickets) and \texttt{MapGraph} (the board as sets of transport modes between adjacent nodes). A thin \texttt{GameService} keeps the live games, locks a game for every call, resolves player tokens and publishes new state. This split came from a mid-project rewrite. Originally the rules were spread through the Spring service and a lobby/Mr~X/detective class hierarchy, which made them hard to test without mocking the graph. With the rules in a plain class, a test builds a game on a small hand-drawn map with exact start positions and checks one rule at a time. Unlimited tickets are stored as $-1$, so Mr~X and detectives share one ticket model, and the random source and clock are injected so a test can fix the roles or jump 15 minutes ahead.

\subsection{Hidden Information and Role-Filtered State}\label{sec:hidden}
\reqs{F4 (goal~2)}
Goal~2 is achieved by never building a message that contains Mr~X's position for anyone but him. \texttt{Game.viewFor(viewer)} builds a separate snapshot for each viewer: Mr~X sees everything, and anyone else sees his node only after he has finished a move in a reveal round. Mr~X's move log carries his node only on a reveal round's final leg, the same for every viewer. After every change, the server publishes the public view to the game's topic, each player's own view to a private topic, and the legal moves to the player whose turn it is (Fig.~\ref{fig:sequence}).

Filtering the payload is necessary but not sufficient: a detective must also be unable to \emph{obtain} Mr~X's view. A late-project review found that the first implementation failed this in several ways. Player identifiers, which every client receives, doubled as credentials, so any player could request Mr~X's view. The in-memory STOMP broker honoured wildcard subscriptions such as \texttt{/topic/games/\{id\}/players/**}, delivering every private view to an eavesdropper. It also relayed messages that clients sent to a topic as if the server had sent them. The redesign separates identity from authority:
\begin{itemize}
	\item Each player receives a random secret \emph{token} only in the response to their own create or join call. Every action carries it in an \texttt{X-Player-Token} header; the public identifier grants nothing.
	\item Private topics are named by the token, and the broker matches destinations exactly, so a wildcard subscription receives nothing.
	\item The server drops every message a client tries to send over STOMP, so clients can only listen.
\end{itemize}
Accounts and logins were considered and rejected: they add friction to a casual game among friends and protect nothing a per-game secret does not.

\subsection{Map Data Design}\label{sec:mapdesign}
\reqs{F7, C1}
The board is a static JSON file of nodes, with latitude and longitude, and undirected edges, each listing its transport modes and a pre-computed line of coordinates along the real road or rail line. The server reads it once at start-up, validates it (an unknown mode or a dangling edge stops the server) and serves it to every client.

Live routing was the first idea and was rejected on cost and speed. Each edge needs a road path between two nodes. With about 400 edges and a directions service billed per request beyond a small free monthly allowance \cite{googlemaps_pricing}, every board load, or a cache to avoid repeating it, would add cost (C1); and an early prototype using a routing plug-in for Leaflet became unresponsive with a few hundred routes. The network does not change during a game, so paths are computed once, offline, from OSM road data, and stored with the graph. At run time the cost is one file download.

The graph's shape was designed for play rather than as an exact copy of the transport network (Fig.~\ref{fig:graph}). Five clusters cover Wellington city, the Hutt Valley and the northern suburbs. Within each, nodes are joined by e-scooter and bus edges along streets, so most moves are short and local. A few train edges join the clusters quickly, and a ferry crosses the harbour. This mirrors the board game, where plentiful short moves are mixed with scarce long jumps, and the detectives' limited train and ferry tickets (6 and 2) make those jumps a resource to manage. Every edge is labelled with low-emission modes only, in keeping with Wellington's public transport and shared e-scooters. The train and ferry edges follow the real rail lines and harbour crossing, but bus and e-scooter edges simply follow Wellington roads; the map creator does not check them against real bus routes or e-scooter operating zones, so they represent what each mode could plausibly do rather than the actual network.

\subsection{User Interface Design}\label{sec:ui}
\reqs{F1, N1, N3}
The interface has six screens: home, create, join, lobby, game board and game over (Figs.~\ref{fig:board} and~\ref{fig:pages}). The lobby is the screen where players wait for the game to start. At the top it shows three ways for the host to invite others: the six-character join code, a link that opens the join page with the code already filled in, and a QR code of that link. The QR code was added with an Open Day stand in mind, so a visitor could scan it and join from their phone. The board (Fig.~\ref{fig:board}) splits the window between the map and a side panel. The map draws each edge in its mode's colour and each node as a small pie chart of the modes that stop there; players appear as rings in their own colour with a role symbol. The side panel lists players, the viewer's tickets, Mr~X's ticket log with reveal rows, every reachable node with a button for each ticket that can pay for it, and the move to confirm. Clicking a reachable node on the map opens the same ticket buttons beside the node, so a move can be made without looking away from the map.

\emph{Designing for committed players.} Both audiences in Section~\ref{sec:requirements} arrive having already decided to play: friends have agreed on a game, and Open Day visitors have been introduced to it by a demonstrator. The interface therefore does not need to grab attention in the first 30~seconds, as an app competing in a store or a casual web game must, and this changed several design choices:
\begin{itemize}
	\item The home page is a title and two buttons, Create and Join, with no splash screen, introductory animation, sound or reward loop. Effort went into the board, where players spend their time.
	\item The board is information-dense rather than minimal. The side panel shows every player, every ticket count, the full Mr~X log and every reachable node at once, because committed players use all of it to plan and a sparse first impression is not the goal.
	\item The full 24-round game was kept, with its 30--60 minute length, instead of being shortened into a quick session to keep a casual visitor hooked.
	\item The rules are not taught by the interface. A host or demonstrator explains them in person, so the screen can assume a player who knows what a reveal round is. The cost is that new players asked for a tutorial (Section~\ref{sec:users}), which remains future work.
	\item There is no automatic skip of a slow turn: committed players are expected to think, and only a 15-minute idle limit protects against an abandoned tab.
\end{itemize}

Several of these features came from user testing (Section~\ref{sec:users}): the transport-mode popups, the taller move list, the centred turn indicator and the reveal rows in the log. A dark basemap was chosen so the four mode colours stand out; a light and a ``Voyager'' style are available for personal preference.

\subsection{Real-World Issues}\label{sec:realworld}
\reqs{C2, C4}
\emph{Sustainable transport.} The game's world contains only e-scooters, buses, trains and a ferry. Players spend 24 rounds planning journeys across the region on those modes alone, along real streets and the real rail lines and ferry crossing. This fits United Nations Sustainable Development Goal~11, sustainable cities and communities \cite{un_sdg}, though no claim is made that playing changes how anyone travels.

\emph{Sustainable software.} The same priority applied to every infrastructure decision. Pre-computing routes replaces hundreds of routing requests per game with one static file. The server is a single process in a 231~MB container image on hardware the author already owned, with no database, no cloud services and no new devices. The whole stack is open source, so the game is not tied to a vendor's pricing or lifetime. The one remaining inefficiency, an uncompressed 1.86~MB map file, is discussed in Section~\ref{sec:discussion}.

\emph{Safety and social impact.} Games like Pok\'emon GO require players to walk around real streets, which raises safety concerns such as traffic. In this game only the players' pieces move on the map, while the players stay at their computers, so it is safe to play and open to people who cannot easily travel, including those with limited mobility. The game is also social: detectives talk to each other to plan their moves. At the Open Day, it showed prospective students a working game built in an engineering degree.

\emph{Privacy and ethics.} The game stores no accounts, email addresses or locations; a player's name lives in memory only until the game ends. User testing was voluntary, involved fellow students, and was covered by the approval the course coordinator gave at the proposal stage. Questionnaire responses were anonymised by removing the email column before analysis.

\subsection{Server}\label{sec:server}
\reqs{F1--F6}
The backend is about 770 lines of Java code (1,460 including documentation) in 22 files.

When a player submits a move, \texttt{Game.move} checks, in order, that:
\begin{enumerate}
	\item the game is in progress and it is this player's turn;
	\item the ticket is valid (the first half of a double move is sent as, for example, \texttt{DOUBLE\_BUS}, and a second double cannot be started during a double);
	\item the two nodes are connected;
	\item the ticket matches a transport mode on that connection, unless it is an Invisible ticket;
	\item the player still has that ticket;
	\item Mr~X is not moving onto a detective.
\end{enumerate}
Only if every check passes are the ticket spent and the player moved, so a rejected move changes nothing. The turn then passes on. After Mr~X moves, it goes to the first detective who can move; after a detective, to the next detective, or to a new round once all have moved. Before each of Mr~X's turns, the server checks that he has a legal move; if he does not, the detectives win.

Several players can send requests to the same game at the same moment, for example two players joining at once. To stop these requests interfering with each other, each game has its own lock: the server handles one request for a game at a time, while different games run in parallel. Making requests within a game wait for each other costs little, because a game only receives a few requests per second.

Every 30~s, the server checks for games where the current player has not moved within the idle limit and ends them. Settings such as the detectives' ticket counts, the idle limit and which map file to load are all kept in one configuration file.

\subsection{Client}\label{sec:client}
\reqs{F7, N1}
The frontend is 23 source files and about 2,400 lines. Game state is one Vue \texttt{reactive()} object that every page and component reads; a state-management library (Pinia) was used at first and removed, because two small stores did not justify a dependency. All server traffic goes through one module, \texttt{api.ts}: a single helper for REST calls, and \texttt{keepUpToDate()}, which opens the STOMP connection and maps each topic to a handler. The map component is the largest file, at about 700 lines. It loads the graph from the server, adds it as GeoJSON sources, draws one line layer per mode with small offsets so parallel modes sit side by side, and pre-draws the 16 possible pie icons for node mode combinations.

\subsection{Resilience to Dropped Connections}\label{sec:resilience}
\reqs{N2}
The original design paused a game when a player disconnected and resumed it within a 60~s grace period. User testing on university and home Wi-Fi showed WebSockets dropping far more often than expected, so pausing would have interrupted games constantly. The design changed so that a dropped connection is not a game event at all. The STOMP client reconnects automatically, re-subscribes, and immediately fetches the full state over REST; a REST refresh also runs every 6~s regardless. Because every message is a complete snapshot rather than a change, a missed message costs at most one refresh interval and can never leave a client inconsistent. This is why the server sends whole views rather than differences, at the price of slightly larger messages.

\subsection{Building the Wellington Map}\label{sec:mapbuild}
\reqs{F7, C1}
Building the map was the hardest part of the project, and the rest of the game could not be fully tested until it was done. Road data for the region was exported from OSM with Overpass Turbo (about 5.7~MB of GeoJSON), and train lines were traced separately. A first approach that laid OSM road segments under each edge produced loops and doubled lines where segments overlapped. Fully automatic generation tended to connect every node to every neighbour, and some routed paths between node pairs wandered far from the direct line.

The solution was a dedicated browser tool, the \emph{map creator}, built on MapLibre. It snaps nodes to the road network, routes each edge along roads with Dijkstra's shortest-path algorithm, and generates the network in layers: train stations and lines first, then bus clusters around each area, then e-scooter edges limited to short distances (at most 900~m). A road-use registry stops two edges claiming the same street, which removed the doubled lines. Generation is followed by manual editing (adding, joining, re-moding and renumbering nodes, with undo), a connected-components view to make sure every node is reachable, and export. The tool was later refactored from one 2,500-line file into nine modules of about 1,500 lines in total, and its output was checked byte for byte against the original before any behaviour changed.

\subsection{Deployment}\label{sec:deploy}
\reqs{C2}
The Docker build compiles the frontend, copies it into the server's static folder and packages a single Java archive; the running container is one Java process that serves the pages, the REST API and the WebSocket endpoint. An earlier image ran nginx beside the server under a process supervisor, with a generated nginx configuration of over 100 lines. Removing it took away a process and a configuration language without losing anything, since Spring can serve static files under the same base path. A deploy script rebuilds from a Git tag, swaps the container and deletes old images, and a Cloudflare Tunnel publishes the server over HTTPS without opening ports on the home network.

\subsection{Development Process and Use of AI}\label{sec:process}
Development ran in short iterations, each ending in something runnable: planning and the map-library benchmark (March--May), the lobby (May), game logic and map rendering (June), the map creator and Wellington graph (June--August), Docker deployment (July--August), user testing (August--September), and a review, rewrite and refactoring phase (September). The repository holds 136 commits.

\emph{AI-assisted development.} Claude Code, a command-line AI coding assistant, was used throughout. It drafted code and tests from written specifications, reviewed code for bugs, carried out refactorings, and kept documentation and diagrams consistent with the code. It was most useful for repetitive changes across many files, such as renaming something in 20 places, and for reviewing code. An AI-assisted code review found two of the most serious bugs: the security weakness that let players see Mr~X's position (Section~\ref{sec:hidden}), and a bug where the game froze if Mr~X had no legal move. Its weaknesses were just as clear. It produced plausible but wrong documentation (for example, describing a pause-on-disconnect feature that had been removed), it tended to add layers and abstractions that were not needed, and early tests it wrote often checked getters rather than behaviour, which a coverage figure alone would not reveal. Not every AI-generated change was reviewed line by line, so the project relied on automated checks to catch mistakes: the automated test suite; mutation testing, which showed whether the tests really checked behaviour (Section~\ref{sec:correctness}); and a local pre-commit hook that rejected any commit changing the API without also updating the OpenAPI file, so the frontend and backend could not silently fall out of step.
% CHECK: confirm how the course wants AI use in writing this report to be disclosed, and add a statement if required.

\emph{Tool critique.} Spring's simple broker made STOMP quick to adopt, but its permissive defaults (wildcard subscriptions, client publishing to topics) caused the most serious bug: a framework's convenient defaults are not necessarily secure ones. MapLibre performed well, but version~4.7 ignored the first resize of its container, leaving a half-blank map in tabs that opened in the background; a resize observer fixed it. SockJS remains useful on restrictive networks, but its client is no longer actively developed and could be replaced by STOMP over a plain WebSocket if the fallback proves unnecessary. Selenium, used first for an end-to-end test, acted only as an HTTP client and was flaky; a browserless test with real HTTP and STOMP clients replaced it, and Playwright was used for scripted browser checks instead.

\subsection{Functional Correctness}\label{sec:correctness}
The backend has 135 automated tests in six layers (Table~\ref{tab:tests}), all passing on the final version, and none needing a browser. Unit tests build games on hand-drawn maps of five to eight nodes with fixed start positions, so each rule is tested against an exact expected outcome: for example, that both legs of a double move happen before any detective moves, that a reveal shows only the second leg's node, or that a detective with no legal move is skipped without spending a ticket. Integration tests run the real server and talk to it over HTTP and STOMP. Functional tests play complete games with one HTTP and one STOMP client per player, checking the game's invariants after every move.

\emph{Regression tests.} The late-project review found eight bugs, three of them high severity: the game froze when Mr~X was boxed in (which also made an earlier end-to-end test fail at random, because 30\% of four-player starts on the small test map box him in on turn~1); any player could see Mr~X's position or act as another player (Section~\ref{sec:hidden}); and a detective leaving froze the game or skipped a turn. Each fix has at least one test that failed before it. The two STOMP attacks were written as tests and run against the old configuration, where the eavesdropper did receive Mr~X's private view, before the fix made them pass.

\emph{Testing the tests.} Coverage shows what tests execute, not what they check, so three measures were used:
\begin{itemize}
	\item \emph{Coverage} (JaCoCo): 99.2\% of lines and 97.8\% of branches across the backend, up from 65\% and 45\% before the rewrite, when the rules engine was mocked out of most tests.
	\item \emph{Mutation testing} with PIT introduces small faults, such as flipping a comparison or deleting a call, and checks that some test fails. All 199 mutants generated in the rules and service code were killed.
	\item \emph{Property-based and fuzz testing}: 300 seeded random games on the real map, each checked after every move for invariants such as ``Mr~X's node never appears in a detective's view outside a reveal'', ``no ticket count goes negative'' and ``every game ends''; and random JSON sent to every endpoint, which must never cause a server error.
\end{itemize}
The frontend has no automated tests. It was manually tested after each update.

\emph{Browser support (N1).} The game was developed and play-tested in Firefox and Chromium-based browsers. Safari was not tested systematically as the author does not have access to an apple device.

\subsection{User Evaluation}\label{sec:users}
Two rounds of play-testing with fellow students shaped the interface, and players also completed the SUS questionnaire.

\emph{Open Day.} The game was demonstrated at a university Open Day, where visitors played it on the stand's laptops. The demonstration was a success. One planned feature did not work out: the lobby's QR code (Section~\ref{sec:ui}) was meant to let visitors join from their phones. Joining by phone works, but the board was designed for a desktop screen, and on a phone the map and side panel do not fit well enough to play, so in practice the QR code was of little use.

\emph{Iterative rounds.} After each round the observed problems were listed and fixed before the next (Table~\ref{tab:feedback}). Round~1 exposed basic usability gaps; round~2 found only presentation issues, suggesting the first round's fixes worked.

\emph{SUS results.} Seven players (six detectives and one Mr~X, in games of four to six players) completed the questionnaire after a full game. The overall mean was 72.5 (range 60--95): 72.9 for detectives ($n=6$) and 70.0 for Mr~X ($n=1$). This is above the average of 68 \cite{sauro2011sus}, meeting N3. In free-text comments, three of the seven asked for a tutorial or rules walk-through; others found the Mr~X log hard to read at first or the reachable-node list cramped on small screens, praised the game as fun and replayable, and asked for custom lobby rules.

\emph{Limitations.} Seven participants is too few for a precise score: one respondent can move the mean by several points. Only one participant played Mr~X, and the questionnaire was given after the round-2 fixes, so there is no before-and-after comparison. The participants were all students. They may be more at ease with new software than the general public, but they are also the audience the game was built for: students playing with friends, and the prospective students who visit an Open Day.

\section{Discussion}\label{sec:discussion}

\emph{What worked.} Three decisions carried the project. Pre-computing the map turned the most expensive and least predictable part of the design, routing, into a one-off offline task with no per-request cost. Putting the rules in a plain class, separate from the framework, made exhaustive and exact tests possible; the rise from 65\% to 99\% coverage came mostly from that change rather than from writing more tests. Sending complete, per-viewer snapshots made both secrecy and resilience simple: there is no client-side game logic that could leak, and no sequence of updates that a missed message could corrupt.

\emph{What was hard.} Building a playable map took far longer than any code. Real road networks are messy, and a graph that is fun to play needs judgement about density, connectivity and the balance between modes that no generator captured on its own. Connection drops on real networks also forced a late design change; the lesson is to treat connectivity as unreliable from the start rather than as an exception.

\emph{Security lesson.} The most serious defect was not in the game rules but in configuration: identifiers that doubled as credentials, and a message broker that by default allowed wildcard subscriptions and client publishing. Filtering the payload correctly was not enough, because the attack went around it. The existing tests did not catch it, because they only checked that the game worked when players used it as intended. It was found by testers and a code review that deliberately tried to get Mr~X's position. When keeping a secret is a core requirement, the tests need to include attempts to break the system, not just normal use.

\emph{Trade-offs revisited.} With no database, a restart ends every game; for short games among friends on a home server this has not been a problem, but it rules out long or scheduled games. The map file is sent uncompressed at 1.86~MB because its edge paths hold about 28,000 coordinate pairs at full precision; HTTP compression and rounding to about one-metre precision would shrink it several-fold with no visible difference, saving data on every board load. The desktop-first layout suits the intended setting but rules out phone play, which also makes the lobby's QR code largely redundant.

\emph{Threats to validity.} The Open Day demonstration was observed informally rather than measured; the benchmark used one browser on one machine; the user study is small and homogeneous; and the frontend's correctness rests on manual tests rather than an automated suite.

\section{Conclusions and Future Work}\label{sec:conclusion}

This project built a browser-based, real-time hidden-movement game on a real map of Wellington. An authoritative Java server enforces every rule and sends each player a separately built view, so Mr~X's position never reaches a detective's device outside a reveal round. A Vue and MapLibre client draws a pre-computed 216-node graph over open map data. All three goals were met: every rule is enforced and tested, with all 199 mutants killed; the secret holds against deliberate attacks on both the REST and STOMP interfaces; and players rated usability 72.5 on the SUS. The game is deployed and can be joined by anyone with a link, over the internet, from any desktop browser, and it has already been run successfully as an Open Day demonstration.

The finished system opens several projects for a future student:
\begin{itemize}
	\item \emph{Computer players and game balance.} Computer-controlled players would allow a single-player mode. They would also make it possible to check whether the game is fair: by having computer players play thousands of games against each other, a student could measure how often each side wins and how that changes with the number of tickets, the reveal rounds or the layout of the map. This is practical because the rules are in one self-contained, well-tested class that can run games without the server.
	\item \emph{Boards for any city.} The map creator's layered generation could become a pipeline from open transport data to a playable board, with balance checked by those bots, so the game could be played on any city.
	\item \emph{Distributed, persistent games.} Persistence and accounts would allow slow games played over days, and running games across several server instances would make the system a test bed for keeping distributed state consistent while preserving per-player secrecy.
	\item \emph{Open Days and a more faithful map.} Building on the successful Open Day, a short tutorial (the most common user request), a mobile layout and a ``spectator'' view for a projector would make the game easier to run with the public, and a structured study at a future Open Day could measure visitors' experience. Building bus and e-scooter edges from real bus route data and e-scooter operating zones would make the board a faithful model of the network; a study could then measure whether playing improves players' knowledge of it.
	\item \emph{Onboarding and reach.} Configurable lobby rules and a larger user study with more Mr~X players.
\end{itemize}
